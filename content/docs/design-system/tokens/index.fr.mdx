## La base de chaque interface [#the-foundation-of-every-interface]

Les tokens de conception sont les **Une seule source de vérité** pour le langage visuel de PyColors UI.

Ils encodent les petites décisions que chaque composant peut consommer :

- rayon
- dénivelé
- Rôles de couleur
- rôles typographiques
- futures règles de mouvement, d'espacement et de superposition

Les tokens ne sont pas des composants. Ce ne sont pas des valeurs CSS aléatoires. Ils sont **décisions de conception exprimées en variables réutilisables**.

<Callout title="Pourquoi cela compte">
  Sans tokens, chaque composant commence lentement à prendre ses propres
  décisions visuelles. Cela crée une dérive, rend les refactors risqués et
  affaiblit le sentiment de prime du produit au fil du temps.

</Callout>

## Jumeler les surfaces avec leurs tokens de premier plan [#pair-surfaces-with-their-foreground-tokens]

Utilisation `primary` avec `primary-foreground`et `destructive` avec `destructive-foreground`. Leurs premiers plans utilisent du texte sombre en mode sombre parce que ces surfaces sémantiques deviennent plus claires; le texte blanc codé en dur ne conserve pas de contraste lisible. Le mode lumière `muted-foreground` supporte également le texte sur la surface en sourdine. Les palettes personnalisées, l'opacité et les arrière-plans superposés nécessitent toujours des contrôles de contraste dans leur contexte réel.

## Étapes [#steps]

<Steps>

<Step>
### Commencez par les décisions de conception [#start-from-design-decisions]

Un token existe lorsqu'une décision visuelle doit être partagée par le système.

Au lieu de demander à chaque composant de décider de son propre rayon, ombre ou traitement de surface, PyColors définit ces décisions une fois.

```text title="system-flow.txt"
Design decisions
  ↓
Tokens
  ↓
Tailwind utilities
  ↓
UI components
  ↓
Product surfaces
```

Ce flux maintient les composants petits pendant que le système reste expressif.

</Step>

<Step>
### Définir les tokens de manière centralisée [#define-tokens-centrally]

Les tokens sont définis comme des variables CSS et mappés dans des utilitaires.

```css title="tokens.css"
:root {
  --radius: 0.625rem;
}

@theme inline {
  --radius-md: calc(var(--radius) - 2px);
  --radius-lg: var(--radius);
  --radius-xl: calc(var(--radius) + 4px);
}
```

La valeur brute reste dans la couche de token. Les composants consomment l'utilité.

```tsx title="components/product-card.tsx"
export function ProductCard() {
  return (
    <article className="rounded-lg border bg-card p-6 shadow-sm">
      <h2 className="text-lg font-semibold tracking-tight">Product surface</h2>
      <p className="mt-2 text-sm leading-6 text-muted-foreground">
        This surface consumes tokens indirectly through utilities.
      </p>
    </article>
  );
}
```

</Step>

<Step>
### Étendre uniquement lorsque le système en a besoin [#extend-only-when-the-system-needs-it]

Toutes les valeurs visuelles n’ont pas besoin de devenir un token le premier jour.

Un nouveau token devrait exister lorsqu'il :

- apparaît à plusieurs endroits
- exprime une décision de produit réutilisable
- améliore le thème ou la cohérence
- réduit le style local dupliqué
- Rendre les changements futurs plus sûrs

<Callout type="info" title="Règle du système">
  Identifiez les décisions de conception répétées, pas les préférences visuelles
  uniques.

</Callout>

</Step>

</Steps>

## Catégories de tokens [#token-categories]

PyColors commence intentionnellement avec une petite surface de token. Cela permet de garder le système compréhensible et évite l'étalement des tokens trop tôt.

| Catégorie   | Objet                                                                  | Situation actuelle |
| ----------- | ---------------------------------------------------------------------- | ------------------ |
| Arrondi     | Géométrie d'angle pour les commandes, les cartes et les superpositions | Actif              |
| Ombres      | Élévation pour surfaces et couches flottantes                          | Actif              |
| Couleurs    | Rôles sémantiques de surface, de texte, d'état et de graphique         | Actif              |
| Typographie | Rôles de police, hiérarchie, étiquettes et densité                     | Actif              |
| Espacement  | Rythme et densité de mise en page du produit                           | Futurs             |
| Motion      | Transitions, assouplissement et interaction                            | Futurs             |
| Z-index     | Règles de superposition pour les superpositions et la navigation       | Futurs             |

<Callout title="Pourquoi la surface est intentionnellement petite">
  Un système de tokens plus petit est plus facile à comprendre, à documenter et
  à maintenir. PyColors ajoute des tokens quand ils clarifient le système, pas
  quand ils créent du vocabulaire supplémentaire.

</Callout>

## Guide de décision [#decision-guide]

Utilisez un token lorsque :

- la valeur apparaît sur plusieurs composants
- Le changer à l'échelle mondiale serait utile
- la valeur porte la signification du produit
- il améliore la cohérence à travers le mode clair et sombre
- il empêche les équipes d’inventer des alternatives locales

Évitez de créer un token lorsque :

- la valeur est purement décorative
- Il n'apparaît qu'une seule fois
- Le nom serait vague
- le token duplique un rôle existant
- Cela rend le système plus difficile à comprendre

## Questions courantes [#common-questions]

<Accordions type="single">
  <Accordion title="Les tokens sont-ils les mêmes que les utilitaires Tailwind?">
    Non. Les tokens définissent la valeur et l'intention. Les utilitaires exposent ces tokens aux composants. Un composant doit consommer l'utilitaire, pas hardcode la valeur brute.
  </Accordion>

<Accordion title="Chaque valeur de conception devrait-elle devenir un token?">
  Non. Les tokens doivent représenter des décisions répétées du système.
  Tokeniser chaque valeur trop tôt crée de la complexité sans améliorer la
  cohérence.
</Accordion>

  <Accordion title="Puis-je personnaliser les valeurs de token ?">
    Oui. L’objectif est de maintenir les rôles publics stables tout en permettant aux valeurs sous-jacentes de changer. Cela vous donne la flexibilité du thème sans réécrire les composants.
  </Accordion>
</Accordions>
