## Vue d’ensemble [#overview]

Couleurs dans PyColors UI sont conçus comme **Rôles sémantiques des produits**Pas de valeurs décoratives.

Le système donne à chaque couche d'interface une signification stable: surfaces de page, cartes, texte, actions, états, bordures, contrôles de formulaire, barres latérales et graphiques. Les composants consomment ces rôles à travers des utilitaires comme `bg-card`, `text-foreground`, `text-muted-foreground`, `bg-primary`et `border-border` au lieu de coder les valeurs visuelles localement.

À la fin de cette page, vous comprendrez comment PyColors structure les rôles de couleur, comment le mode clair et sombre reste prévisible et comment appliquer les décisions de couleur sans créer de dérive de thème.

<Callout title="Pourquoi cela compte">
  La cohérence des couleurs est l'un des signaux les plus rapides de la qualité
  du produit. Un système de couleurs sémantique maintient les tableaux de bord,
  les pages marketing, la documentation, les formulaires et les composants
  réutilisables visuellement alignés sans forcer chaque composant à réinventer
  sa propre palette.

</Callout>

### Architecture [#architecture]

PyColors utilise une **Système de couleurs basé sur OKLCH** exposés à travers des variables CSS et mappés dans les utilitaires sémantiques Tailwind.

OKLCH donne à la couche de tokens un contrôle plus prévisible sur la légèreté perçue, le contraste et l'équilibre du thème que les valeurs RVB brutes ou HSL uniques. C'est important lorsqu'un produit doit prendre en charge le mode lumière, le mode sombre, les composants d'interface utilisateur réutilisables, les longues pages de documentation, les tableaux de bord, les écrans de paramètres et les surfaces commerciales.

<Callout type="info" title="Principe de base">
  Les composants doivent consommer des rôles de couleur. La couche de tokens
  devrait décider de l'apparence de ces rôles.

</Callout>

## Modèle de rôle [#role-model]

PyColors regroupe les couleurs par responsabilité du produit. Cela permet de garder le système plus facile à raisonner et empêche la table des matières de devenir bruyante.

| Catégorie  | Tokens                                              | Utilisé pour                                                    |
| ---------- | --------------------------------------------------- | --------------------------------------------------------------- |
| Surfaces   | `background`, `card`, `popover`, `sidebar`          | Calques, cartes, superpositions, navigation                     |
| Texte      | `foreground`, `muted-foreground`, `card-foreground` | Copie primaire, copie secondaire, texte spécifique à la surface |
| Actions    | `primary`, `secondary`, `accent`, `muted`           | Boutons, accent, zones d'interaction subtiles                   |
| États      | `destructive`, `success`, `warning`                 | Feedback produit, validation, risque, confirmation              |
| Apports    | `border`, `input`, `ring`                           | Formes, états de focus, séparateurs, contours de contrôle       |
| Graphiques | `chart-1` au `chart-5`                              | Visualisation des données uniquement                            |

<Callout title="Pourquoi cela compte">
  La séparation des rôles d'interface utilisateur des rôles de graphique empêche
  les couleurs de visualisation des données de s'infiltrer dans les états du
  produit. Une palette graphique ne doit pas devenir la source de vérité pour
  les boutons, les alertes ou les actions destructrices.

</Callout>

## Exécution [#implementation]

Utilisez des utilitaires sémantiques dans chaque composant réutilisable.

```tsx title="recommended.tsx" {3-8}
export function ProductNotice() {
  return (
    <div className="rounded-2xl border border-border bg-card p-5 text-card-foreground">
      <p className="text-sm font-medium text-foreground">
        Production-ready surface
      </p>
      <p className="mt-1 text-sm text-muted-foreground">
        The visual intent comes from the design system, not from local
        overrides.
      </p>
    </div>
  );
}
```

Évitez les valeurs brutes à l'intérieur de l'interface utilisateur réutilisable.

```tsx title="avoid.tsx" {3-5}
export function ProductNotice() {
  return (
    <div className="rounded-2xl border border-[#e5e7eb] bg-[#ffffff] p-5 text-[#111827]">
      <p className="text-sm text-[#6b7280]">This creates theme drift.</p>
    </div>
  );
}
```

<Callout type="warn" title="Piège commun">
  Ne résolvez pas les besoins de couleurs répétés avec des remplacements locaux.
  Si la même intention visuelle apparaît à plusieurs endroits, définissez ou
  ajustez plutôt le rôle sémantique.

</Callout>

## Guide de décision [#decision-guide]

Utilisez les rôles de couleur sémantiques PyColors lorsque :

- Le composant est réutilisable
- l'interface utilisateur doit prendre en charge le mode clair et sombre
- la surface apparaît dans les tableaux de bord, les documents, le marketing ou les paramètres
- la même signification visuelle doit rester stable sur l'ensemble du produit
- Les mises à jour du thème doivent être centralisées

Évitez les valeurs brutes locales lorsque :

- le composant appartient au système de conception
- la valeur représente un état de produit
- la couleur affecte le contraste du texte ou la visibilité du focus
- la couleur sera probablement réutilisée ailleurs
- la valeur doit survivre aux changements de thème futurs

## Erreurs courantes [#common-mistakes]

<Accordions type="single">
  <Accordion title="Utilisation des valeurs hexadécimales brutes dans les composants réutilisables">
    Les valeurs brutes créent une dérive de thème, rendent le mode sombre plus difficile à maintenir et cachent les décisions visuelles à l'intérieur de l'implémentation des composants. Préférez les utilitaires tels que `bg-card`, `text-muted-foreground`et `border-border`.
  </Accordion>

<Accordion title="Réutiliser les couleurs des graphiques pour les états de produits">
  Les couleurs des graphiques sont utilisées pour la visualisation des données.
  Les états de produit tels que le succès, l'avertissement et les actions
  destructrices nécessitent des rôles sémantiques dédiés afin que les
  commentaires restent cohérents.
</Accordion>

<Accordion title="Traiter l’accent comme une décoration">
  `accent` Il faut mettre l’accent intentionnellement. Si chaque section invente
  un comportement d'accent différent, le produit commence à se sentir
  incohérent.
</Accordion>

<Accordion title="Fixation d'un écran au lieu du calque de tokens">
  Les correctifs locaux résolvent l'écran actuel, mais créent des coûts de
  maintenance à long terme. Si le besoin se répète, mettez à jour le rôle
  sémantique de manière centralisée.
</Accordion>

  <Accordion title="Sauter les contrôles de contraste en mode sombre">
    Chaque rôle utilisé pour le texte, les actions, les entrées et les états doit rester lisible en mode clair et sombre avant l'expédition.
  </Accordion>
</Accordions>
