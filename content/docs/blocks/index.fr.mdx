[Explorez le catalogue Blocks](/blocks) choisir un shell d'application, un panneau d'authentification, une surface de commerce, une table de données, une surface de compte / espace de travail, un état vide ou un autre modèle documenté avant de suivre les étapes d'installation ci-dessous.

Dans le catalogue, ouvrez **Code** pour inspecter la source complète et sa structure de dossiers. L'arborescence des fichiers est visible par défaut à côté du code sur le bureau et au-dessus sur mobile. Utilisation **Fichiers** pour le cacher ou le montrer; les blocs avec plusieurs fichiers ont également un sélecteur de fichiers sur mobile.

**Télécharger ZIP** sauvegarde le bloc complet dans une archive, en préservant le bloc `src/components/blocks/<block-slug>/` structure. Extrayez-le, puis déplacez le dossier du bloc dans votre application. **Copier le fichier** copie uniquement le fichier sélectionné; vous pouvez également sélectionner le code manuellement si la copie n'est pas disponible. Conservez tous les fichiers ensemble et préservez leurs importations relatives.

Les blocs simples restent dans un fichier. Les compositions plus grandes utilisent quelques fichiers ciblés avec un `index.tsx` point d'entrée. Le ZIP contient la même source que celle affichée dans l'explorateur ; configurez React, le package d'interface utilisateur publique et les tokens dans votre propre application.

## Copier la source, puis la posséder [#copy-source-then-own-it]

PyColors Blocks utilise un flux manuel de copie de source. Lorsqu'un bloc est disponible, copiez son répertoire source canonique dans votre application, puis traitez le code copié comme votre propre code produit.

L'installation d'un miroir public nécessite toujours un contrôle de disponibilité séparé. Le flux manuel sur cette page reste supporté et n'est pas remplacé par le pilote.

## Localisation Canonique [#canonical-source-location]

Le dépôt PyColors conserve la source canonique Block à :

```text
apps/marketing/content/blocks/<category-slug>/<block-slug>/
```

Les deux segments de chemin utilisent un kebab minuscule. `<category-slug>` doit être l'un des limaces approuvées ci-dessous, et chaque bloc de production possède une écurie `<block-slug>`.

## Catégories approuvées [#approved-categories]

Chaque bloc a une catégorie primaire. Les balises peuvent prendre en charge la découverte secondaire sans créer d'alias de source ou de catégorie en double.

| Catégorie                      | Slug         | Questions de source-propriétaire |
| ------------------------------ | ------------ | -------------------------------- |
| Coquilles d ' application      | `app-shells` | #94                              |
| Authentification               | `auth`       | #95                              |
| Commerce                       | `commerce`   | — 96 et — 98                     |
| Compte &amp; espace de travail | `account`    | — 97 et — 99                     |
| Données et enregistrements     | `data`       | #101                             |
| Feedback &amp; états           | `feedback`   | #100                             |

La source, la navigation dans la documentation et les métadonnées du Registre utilisent les mêmes `<category-slug>/<block-slug>` Identité. Par exemple, `data/data-table` maps à l'route de documentation `/docs/blocks/data/data-table` et, seulement après une approbation distincte du Registre, l'élément du Registre `data-data-table`.

La disponibilité gratuite et Pro sont des métadonnées distinctes sur cette identité partagée. Ils ne créent pas de taxonomies différentes et n'exposent pas de sources privées.

Les aperçus de documentation doivent importer ou rendre la source de bloc canonique lorsque cela est pratique. Un aperçu n'est jamais une implémentation alternative à copier.

<Callout title="Autorité source">
  `@pycolors/ui` et `@pycolors/tokens` restent les autorités publiques
  primitives et symboliques. Starter Free est une preuve de produit et les
  aperçus de documentation sont des exemples, pas une source de bloc
  alternative. Les artéfacts de registre ne distribuent que la source canonique,
  tandis que le futur Pro reste une autorité distincte sous le numéro 36. La
  première séquence source approuvée était #94, puis #101, puis #97; le
  séquençage courant est coordonné par #35.

</Callout>

## Installer un bloc [#install-a-block]

<Steps>
  <Step>
    ### Copier le répertoire source complet [#copy-the-complete-source-directory]

    Copier le canonique `<block-slug>` dans un emplacement que votre application possède, comme `src/components/blocks/<block-slug>`. Conservez les fichiers locaux du bloc ensemble afin que ses importations relatives restent locales à la source copiée.

    Utilisation **Télécharger ZIP** dans la vue Code du catalogue pour récupérer chaque fichier à la fois, ou copier chaque fichier individuellement. L'archive est assemblée dans votre navigateur à partir de la source affichée. Il n'installe pas de dépendances ou ne met pas à jour votre application.

</Step>

  <Step>
    ### Utiliser les importations publiques de l'interface utilisateur PyColors [#use-public-pycolors-ui-imports]

    Installer et configurer `@pycolors/ui` dans l'application de consommation en suivant les [Guide d'installation](/docs/ui/installation). Le bloc source doit importer les primitives PyColors à partir du point d'entrée du paquet public uniquement lorsqu'il en a besoin.

    ```tsx title="src/components/blocks/<block-slug>/index.tsx"
    import { Button, Card } from "@pycolors/ui";
    ```

    Ne pas utiliser `@pycolors/ui/src/*`, `@pycolors/ui/dist/*`, alias d'applications internes ou privés `@pycolors/*` paquets. Les importations React ou Next ne sont appropriées que lorsque le bloc copié en a réellement besoin.

</Step>

  <Step>
    ### Personnaliser le code copié [#customize-the-copied-code]

    Le code copié appartient à votre application. Adaptez-le à vos routes, votre contenu, votre style, votre état et vos règles produit. PyColors ne met pas automatiquement à jour ou ne synchronise pas la source Block copiée.

</Step>

  <Step>
    ### Valider le résultat [#validate-the-result]

    Exécutez les commandes lint, type-check, test et build de votre application après avoir copié ou personnalisé un bloc. Conservez la sémantique accessible, le comportement du clavier, les étiquettes et les états de focus visibles tout en apportant des modifications.

</Step>

</Steps>

## Contrôles des dépôts [#repository-checks]

Les mainteneurs PyColors valident ce contrat de copie source avec :

```bash
pnpm check:blocks-contract
pnpm test:blocks-contract
pnpm --filter pycolors-marketing lint
pnpm --filter pycolors-marketing types:check
pnpm --filter pycolors-marketing build
```

Le contrôle structurel applique la catégorie exacte allowlist et les noms minuscules de kebab-case, rejette les espaces réservés vides, profond `@pycolors/ui` les importations, les importations internes d'applications ou de paquets, et les artefacts de paquet, de registre ou d'interface de ligne de commande. Il valide le contrat de livraison sans créer un bloc de production d'échantillons.

## Les mises à jour sont délibérées [#updates-are-deliberate]

Les blocs sont des copies sources, pas une dépendance gérée. Si une future version canonique change, examinez-la délibérément et apportez uniquement les modifications qui correspondent à votre application. Votre copie reste sous votre contrôle jusqu'à ce que vous choisissiez de la mettre à jour.
