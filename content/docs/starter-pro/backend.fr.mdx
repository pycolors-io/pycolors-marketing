## Des fondations qui rendent le produit réel [#backend-foundations-that-make-the-product-real]

Starter Free vous donne un **surface SaaS frontale**.

Starter Pro vous donne le **structure backend, modèle de données et fondations côté serveur** nécessaire pour produire un vrai produit.

C'est là que votre application cesse de se comporter comme une démo et commence à se comporter comme un système:

- réelle persistance
- Les vrais utilisateurs
- Propriété réelle
- État de facturation réel
- Règles réelles côté serveur
- Comportement réel du produit

### Ce que cela résout [#what-this-solves]

Beaucoup de produits SaaS n’échouent pas parce que l’interface utilisateur est faible.

Ils échouent parce que le backend devient flou :

- La propriété des données est dupliquée
- auth et facturation ne sont pas connectés proprement
- règles d'accès fuite dans les composants
- La logique du produit est dispersée sur plusieurs pages
- Les décisions de schéma deviennent coûteuses à changer
- Les données simulées deviennent une logique de production fragile

Starter Pro vous donne une base structurée afin que le travail de backend puisse évoluer avec le produit au lieu de le ralentir.

## Architecture [#architecture]

### Responsabilités du modèle de données [#data-model-responsibilities]

Un véritable backend SaaS a besoin de modèles qui représentent la couche métier, pas seulement les données de l’interface utilisateur.

Starter Pro est conçu autour de responsabilités telles que :

| Zone               | Objet                                           |
| ------------------ | ----------------------------------------------- |
| Utilisateur        | Identité, profil, propriété, sessions           |
| Compte             | Connexions fournisseur OAuth                    |
| Session            | Sessions authentifiées actives                  |
| Client             | Relation de facturation avec Stripe             |
| Produit            | Famille de produits ou de régimes vendables     |
| Prix               | Prix Stripe et plan commercial                  |
| Abonnement         | Accès, statut, cycle de vie et renouvellements  |
| Facture            | Historique des paiements et état de facturation |
| WebhookEvent       | Traitement fiable des événements                |
| Modèles de domaine | Vos entités de produits réelles                 |

<Callout type="info" title="Pourquoi cela compte">
  Un backend SaaS n’est pas seulement un CRUD. C’est l’endroit où l’identité,
  les revenus, la propriété et le comportement des produits se rencontrent.

</Callout>

## Voie de mise en œuvre [#implementation-path]

<Steps>
  <Step>
    ### Valider la fondation existante [#validate-the-existing-foundation]

    Avant d'ajouter votre logique de domaine, confirmez que l'authentification, la facturation, la configuration de la base de données et les flux de données d’exemple locales fonctionnent.

</Step>

  <Step>
    ### Définissez votre premier modèle de domaine [#define-your-first-domain-model]

    Ajoutez l'entité produit qui compte le plus à votre SaaS.

```prisma title="schema.prisma"
model Project {
  id        String   @id @default(cuid())
  name      String
  ownerId   String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

</Step>

  <Step>
    ### Ajouter des règles de propriété [#add-ownership-rules]

    Connectez les données produit au modèle utilisateur, client ou organisation authentifié.

```ts title="server/projects/access.ts"
export function canAccessProject(projectOwnerId: string, userId: string) {
  return projectOwnerId === userId;
}
```

</Step>

  <Step>
    ### Conserver la logique du produit côté serveur [#keep-product-logic-server-side]

    L'interface utilisateur doit appeler le flux de produit.

    Il ne devrait pas avoir de règles sensibles.

</Step>

  <Step>
    ### Connecter la facturation si nécessaire [#connect-billing-when-needed]

    Si la fonctionnalité est payante ou dépend du plan, ajoutez des vérifications tenant compte du plan près de la limite du serveur.

</Step>

</Steps>

## Ce que vous évitez de construire vous-même [#what-you-avoid-building-yourself]

Sans Starter Pro, vous devez généralement concevoir et câbler:

- base de données schéma fondations
- relations auth-to-user
- association des comptes aux clients Stripe
- Règles d'accès à l'abonnement
- comportement de la route protégée
- webhook état persistance
- Contrôles de propriété des produits
- règles d'accès de livraison
- patterns de séparation de domaine

C’est souvent long, facile à dupliquer et coûteux à refactoriser plus tard.

### Liste de contrôle de production [#production-checklist]

Avant de traiter le backend comme prêt au lancement, validez :

- Migrations de base de données
- Données sur les données d’exemple
- modèle d'utilisateur
- modèle de session
- association des comptes aux clients Stripe
- État de la souscription
- Gestion des événements webhook
- contrôle de propriété
- Accès aux données protégées
- logique d'accès selon l’offre
- Validation côté serveur
- gestion des erreurs
- variables d'environnement de déploiement

<Callout type="info" title="Principe de validation">
  Ne construisez pas de complexité de nouveau produit sur un backend non validé.
  Confirmez d'abord la fondation.

</Callout>

## Questions courantes [#common-questions]

<Accordions type="single">
  <Accordion title="Starter Pro est-il un produit backend complet ?">
    Non. Il vous donne les fondations backend nécessaires pour lancer plus rapidement. Vous construisez toujours vos modèles de domaine, vos workflows et vos règles spécifiques aux produits.
  </Accordion>

<Accordion title="Puis-je changer le schéma ?">
  Oui. Le schéma est destiné à être étendu. Gardez les limites d'auth, de
  facturation et de propriété claires lorsque vous ajoutez des modèles
  spécifiques au produit.
</Accordion>

<Accordion title="Le contrôle d'accès doit-il être installé sur le frontend ?">
  Non. Le frontend peut refléter l'état d'accès, mais les vérifications
  sensibles doivent être effectuées sur le serveur ou dans une logique
  consciente du backend.
</Accordion>

  <Accordion title="Comment la facturation se connecte-t-elle à la logique backend ?">
    L'état de facturation doit être synchronisé à partir de Stripe et stocké dans votre application afin que la logique côté serveur puisse décider de l'accès de manière fiable.
  </Accordion>
</Accordions>
