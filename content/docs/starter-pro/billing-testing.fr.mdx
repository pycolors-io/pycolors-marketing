## Pourquoi les tests de facturation sont importants [#why-billing-testing-matters]

Les systèmes de facturation sont des systèmes d'État distribués.

Une redirection réussie ne garantit pas un état d'abonnement synchronisé.

Le frontend peut avoir l'air correct alors que l'état du backend est toujours erroné :

- Le checkout peut être complet
- l'utilisateur peut revenir à l'application
- L'abonnement ne peut pas être synchronisé
- accès premium peut rester verrouillé
- Le traitement du webhook peut échouer silencieusement
- état de facturation peut dériver de Stripe

C'est pourquoi la facturation doit être testée comme un cycle de vie, pas comme un bouton.

```txt title="billing-lifecycle.txt"
Checkout
  ↓
Stripe
  ↓
Webhook verification
  ↓
Subscription sync
  ↓
Application billing state
  ↓
Plan-aware access
  ↓
Protected product routes
```

<Callout type="info" title="Aperçu de la production">
  Les bugs de facturation les plus dangereux apparaissent souvent après le
  paiement. Validez le chemin de synchronisation d'état, pas seulement la page
  de paiement.

</Callout>

## Stripe CLI [#stripe-cli]

Utilisez Stripe CLI pour transférer des événements Webhook locaux vers Starter Pro.

```bash title="stripe-cli.sh"
stripe listen --forward-to localhost:3000/api/webhooks/stripe
```

Puis configurez le secret webhook dans `.env.local`.

```bash title=".env.local"
STRIPE_WEBHOOK_SECRET=whsec_xxxxx
```

<Callout title="Règle de Webhook">
  Si le secret du webhook est erroné, la synchronisation de facturation devrait
  échouer en toute sécurité. Ne contournez pas la vérification de webhook
  pendant le développement.

</Callout>

## Flux de validation recommandé [#recommended-validation-flow]

<Steps>
  <Step>
    ### Démarrez l'application locale [#start-the-local-app]

```bash
pnpm dev
```

</Step>

  <Step>
    ### Démarrer Stripe webhook forwarding [#start-stripe-webhook-forwarding]

```bash
stripe listen --forward-to localhost:3000/api/webhooks/stripe
```

</Step>

  <Step>
    ### Démarrez le flux de mise à niveau [#start-the-upgrade-flow]

    Déclenchez le paiement à partir de la tarification, de la facturation ou d'un CTA de mise à niveau.

</Step>

  <Step>
    ### Compléter le paiement en mode test [#complete-checkout-in-test-mode]

    Utilisez une carte de test Stripe et revenez à l'application.

</Step>

  <Step>
    ### Confirmer la synchronisation webhook [#confirm-webhook-synchronization]

    Validez que l'état de l'abonnement a été synchronisé dans votre base de données et reflété dans les routes protégées.

</Step>

  <Step>
    ### Valider le comportement d'accès [#validate-access-behavior]

    Vérifiez que les surfaces premium se comportent correctement après les changements d'état de l'abonnement.

</Step>

</Steps>

## Questions courantes [#common-questions]

<Accordions type="single">
  <Accordion title="Pourquoi les webhooks sont-ils nécessaires ?">
    Parce que les redirections seules ne peuvent pas confirmer ce qui s’est réellement passé à l’intérieur de Stripe. Les webhooks sont la couche de synchronisation backend.
  </Accordion>

<Accordion title="Les contrôles d'accès devraient-ils se faire uniquement côté client?">
  Non. L'accès sensible à la facturation doit rester vérifiable par le serveur.
  L'interface utilisateur peut refléter l'état d'accès, mais le serveur doit
  protéger les ressources précieuses.
</Accordion>

  <Accordion title="Dois-je tester les paiements échoués avant le lancement ?">
    Oui. Les états de paiement et d'annulation échoués font partie du comportement réel du cycle de vie de l'abonnement et ne doivent pas être découverts après le lancement.
  </Accordion>
</Accordions>
