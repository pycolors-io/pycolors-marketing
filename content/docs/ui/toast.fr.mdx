## Rétroaction non bloquante pour les actions produit [#non-blocking-feedback-for-product-actions]

Les **Toast** Le composant affiche des commentaires courts, temporaires et non bloquants.

Utilisez-le pour :

- Confirmer les actions
- Résumer les résultats
- afficher de courts messages système
- fournir une réessai légère ou annuler les commentaires
- Reconnaître l'intention de l'utilisateur sans interrompre le flux

Toast est intentionnellement minime dans PyColors UI.

Il fournit une structure et une accessibilité, et non un système de notification complet avec des files d'attente, des magasins globaux, du dédoublonnage ou un historique de notification persistant.

<Callout title="Idée de base">
  Les toasts sont des commentaires temporaires. Ils devraient confirmer, résumer
  ou récupérer - ne pas bloquer la tâche.

</Callout>

### Importation [#import]

```tsx title="toast-import.tsx"

```

### Utilisation de base [#basic-usage]

Toast est contrôlé explicitement par la page ou le composant.

Enveloppez votre application, votre route ou votre sous-arbre de mise en page avec `ToastProvider`, puis rendre une `ToastViewport` par étendue de fournisseur.

"use client";

import * as React from "react";
import {
  Button,
  Toast,
  ToastProvider,
  ToastViewport,
  ToastTitle,
  ToastDescription,
} from "@pycolors/ui";

export function ToastExample() {
  const [open, setOpen] = React.useState(false);

  return (
    <ToastProvider>
      <Button onClick={() => setOpen(true)} variant="outline" size="sm">
        Trigger toast
      </Button>

      <Toast
        open={open}
        onOpenChange={setOpen}
        variant="success"
        duration={2500}
      >
        <ToastTitle>Changes saved</ToastTitle>
        <ToastDescription>Your settings were updated.</ToastDescription>
      </Toast>

      <ToastViewport className="fixed bottom-4 right-4 z-50 flex max-w-sm flex-col gap-2 outline-none" />
    </ToastProvider>
  );
}

### Variantes [#variants]

Toast prend en charge un petit ensemble de variantes. Les variantes de succès, d'avertissement et de destruction utilisent des couleurs de bordure sémantiques avec le texte de premier plan normal, préservant ainsi le contraste lisible des messages dans les deux thèmes. Inclure un titre descriptif ou un message afin que la signification ne dépende pas uniquement de la couleur. Consommateur `className` Les surcharges ont toujours préséance.

Gardez les variantes limitées pour éviter de transformer chaque message en événement.

### Variantes disponibles [#available-variants]

| Variante      | Objet                                                     |
| ------------- | --------------------------------------------------------- |
| `default`     | Confirmation ou information neutre                        |
| `success`     | Confirmation positive                                     |
| `warning`     | Attention nécessaire, toujours non bloquante              |
| `destructive` | Feedback d'erreur non bloquant                            |
| `info`        | Message d'information - annonce poliment (non affirmatif) |

<Callout type="info" title="Variante de règle">
  Utilisation `destructive` uniquement pour les défaillances récupérables ou non
  bloquantes. Utilisez Alert pour bloquer les erreurs.

</Callout>

### Avec description [#with-description]

Utilisation `ToastDescription` Quand le titre seul ne suffit pas.

```tsx title="toast-description.tsx"
<Toast variant="warning">
  <ToastTitle>Unsaved changes</ToastTitle>
  <ToastDescription>
    Save before leaving this page to avoid losing your work.
  </ToastDescription>
</Toast>
```

Gardez la description courte.

Si le message a besoin de plus d'explications, il appartient probablement à une section Alerte, Boîte de dialogue ou page.

  <Step>
    #### Déclenchement après le début ou la fin de l'action [#trigger-after-the-action-starts-or-completes]

    Utilisez la rétroaction après une action significative : sauvegardée, archivée, restaurée, copiée, échouée ou mise en file d'attente.

  <Step>
    #### Utiliser l'état inline pour un travail actif [#use-inline-state-for-active-work]

</Step>

  <Step>
    #### Utilisez les actions de récupération avec précaution [#use-recovery-actions-carefully]

    Annuler et réessayer fonctionnent bien pour les actions réversibles, mais elles nécessitent un véritable support backend.

</Step>

</Steps>

## Toast vs Alerte vs Dialogue [#toast-vs-alert-vs-dialog]

| Situation                                      | Utilisation    |
| ---------------------------------------------- | -------------- |
| Enregistrer la confirmation                    | Toast          |
| Copie au presse-papiers                        | Toast          |
| Synchronisation d'arrière-plan terminée        | Toast          |
| Erreur de page de blocage                      | Alerte         |
| Problème de validation au niveau du formulaire | Alerte         |
| Confirmation destructive                       | boîte dialogue |
| L'utilisateur doit choisir avant de continuer  | boîte dialogue |

<Callout title="Règle de décision">
  Toast est pour la rétroaction après un flux. L'alerte est pour l'information à
  l'intérieur d'un flux. La boîte de dialogue sert à bloquer les décisions.

</Callout>

## API [#api]

| Prop           | Type                                                   | Par défaut       | Désignation                                     |
| -------------- | ------------------------------------------------------ | ---------------- | ----------------------------------------------- |
| `variant`      | `"default" \| "success" \| "warning" \| "destructive"` | `"default"`      | Style visuel                                    |
| `open`         | `boolean`                                              | —                | État ouvert contrôlé                            |
| `onOpenChange` | `(open: boolean) => void`                              | —                | Gestionnaire d'État                             |
| `duration`     | `number`                                               | Radix par défaut | Délai de fermeture automatique en millisecondes |
| `className`    | `string`                                               | —                | Classes Tailwind personnalisées                 |

### Accessibilité [#accessibility]

- Toast est construit sur les primitives Radix Toast.
- Les toasts ne doivent pas piéger le focus.
- Les toasts ne doivent pas interrompre l'entrée du formulaire.
- Les toasts sont annoncés sous forme de mises à jour en direct de la région, à une urgence qui correspond `variant`:

  | Variante      | Avis                                 | Radix `type`   |
  | ------------- | ------------------------------------ | -------------- |
  | `default`     | Polite - en attente d'une pause      | `"background"` |
  | `success`     | Polite - en attente d'une pause      | `"background"` |
  | `warning`     | Assertive - interrompt immédiatement | `"foreground"` |
  | `destructive` | Assertive - interrompt immédiatement | `"foreground"` |
  | `info`        | Polite - en attente d'une pause      | `"background"` |

  Passez un explicite `type` prop pour remplacer cette valeur par défaut sur un toast spécifique.

- Gardez la copie courte pour que les annonces soient compréhensibles.
- Ne comptez pas uniquement sur la couleur pour les messages destructeurs ou d'avertissement.
- N'utilisez pas Toast comme seul endroit pour les erreurs critiques.

<Callout title="Règle d'accessibilité">
  Les toasts sont utiles quand ils sont courts. Les messages longs ou critiques
  doivent entrer dans la page avec Alert.

</Callout>

### Quand ne pas utiliser Toast [#when-not-to-use-toast]

N'utilisez pas Toast pour:

- Erreurs de blocage
- Validation sur le terrain
- Flux d'intégration
- Centres de notification persistants
- Les échecs de paiement qui bloquent la progression
- Erreurs d'autorisation nécessitant une explication
- messages importants que l'utilisateur doit lire avant de continuer

Utilisez plutôt Alerte, État vide, Boîte de dialogue ou un modèle dédié.

## Questions courantes [#common-questions]

<Accordions type="single">
  <Accordion title="Toast doit-il gérer l'état de notification global ?">
    Pas par défaut. PyColors Toast est intentionnellement minime. Ajoutez un magasin global uniquement lorsque votre produit a besoin d'historique de file d'attente, de déduplication, de persistance ou de notification.
  </Accordion>

<Accordion title="Toast peut-il inclure des actions ?">
  Oui, mais gardez les actions courtes et récupérables, comme Annuler ou
  Réessayer. Si l'utilisateur doit prendre une décision, utilisez la boîte de
  dialogue.
</Accordion>

<Accordion title="Faut-il utiliser le toast ?">
  Seulement des erreurs non bloquantes ou récupérables. Les erreurs de blocage
  doivent utiliser Alert dans le contexte.
</Accordion>

  <Accordion title="Combien de ToastViewports dois-je rendre ?">
    Habituellement un par app ou portée de mise en page. Évitez de rendre une fenêtre d'affichage dans chaque composant.
  </Accordion>
</Accordions>
