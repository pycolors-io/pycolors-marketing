## Données structurées pour les interfaces SaaS [#structured-data-for-saas-interfaces]

Les **Tableau** Le composant affiche des données structurées et comparables.

Utilisez-le pour:

- utilisateurs
- projets
- factures
- Abonnements
- logs
- rapports
- événements audit
- admin records

Le tableau fournit une base visuelle cohérente pour les données produit denses :

- Structure sémantique de table
- design-token style
- Débordement horizontal
- retour hover ligne
- état vide intégré
- état de chargement intégré

<Callout title="Idée de base">
  Utilisez Table lorsque les utilisateurs ont besoin de comparer des
  enregistrements structurés entre colonnes. Utilisez des cartes lorsque le
  contenu est plus éditorial, visuel ou axé sur l'action.

</Callout>

### Légende [#caption]

Utilisation `TableCaption` lorsque la table a besoin d'un résumé concis.

```tsx title="table-caption.tsx"
<Table>
  <TableCaption>List of active users</TableCaption>
  {/* rows */}
</Table>
```

Les sous-titres doivent expliquer ce que contient le tableau, et non répéter le titre de la page.

### État vide [#empty-state]

Utilisation `TableEmpty` lorsque la requête a réussi mais qu'aucune ligne n'est disponible.

<Callout type="info" title="Règle d'état vide">
  Vide n'est pas une erreur. Expliquez pourquoi la table est vide et ce que
  l'utilisateur peut faire ensuite.

</Callout>

### État de chargement [#loading-state]

Utilisation `TableLoading` lorsque la structure de la table est connue mais que les données sont toujours en cours de chargement.

```tsx title="table-loading.tsx"
<TableBody>
  <TableLoading colSpan={3} />
</TableBody>
```

Utilisez le chargement des lignes au lieu de supprimer la table de la page.

Cela préserve la mise en page et réduit le saut visuel.

### Composition du tableau [#table-composition]

Une table de production appartient généralement à une plus grande composition de caractéristiques.

```tsx title="projects-table-section.tsx"
export function ProjectsTableSection() {
  return (
    <section className="space-y-4">
      <ProjectsToolbar />
      <Table>
        <ProjectsTableHeader />
        <ProjectsTableBody />
      </Table>
      <ProjectsPagination />
    </section>
  );
}
```

La table rend la structure.

La couche de fonctionnalité possède:

- récupération de données
- filtres
- tri
- pagination
- autorisations
- mutations
- actions en ligne

<Callout title="Règle d'architecture">
  La table ne doit pas posséder la source de données. Continuez à récupérer,
  filtrer, trier et les mutations dans le calque de fonctionnalités.

</Callout>

## Modèle de table vs carte vs table de données [#table-vs-card-vs-data-table-pattern]

| Situation                                           | Utilisation                  |
| --------------------------------------------------- | ---------------------------- |
| Données structurées comparables                     | Tableau                      |
| Éléments visuels ou lourds de contenu               | Carte                        |
| Petite liste avec une action principale par élément | Carte ou liste personnalisée |
| Filtres, pagination, actions en ligne, états        | Tableaux de données          |
| Chronologie ou flux d'activité                      | Liste personnalisée          |
| Navigation mobile-first                             | Cartes ou liste responsive   |

<Callout type="info" title="Règle de décision">
  La table est primitive. Data Table Pattern est l'expérience produit complète
  qui l'entoure.

</Callout>

### Accessibilité [#accessibility]

Les tables doivent préserver la structure sémantique.

Directives :

- utilisation `TableHead` pour les en-têtes de colonne - il vaut par défaut `scope="col"`, ainsi l'association de colonne est correcte sans n'importe quels accessoires supplémentaires
- pass `scope="row"` explicitement sur a `TableHead` utilisé comme en-tête de ligne
- inclure une légende lorsque le contexte n'est pas évident
- éviter d'utiliser des tables pour la mise en page
- Gardez les cellules lisibles et concises
- s'assurer que les actions de ligne interactives sont accessibles au clavier
- éviter de rendre la ligne entière cliquable à moins que l'interaction ne soit claire
- utiliser des étiquettes visibles pour les actions de ligne icon-only

<Callout title="Règle d'accessibilité">
  Les tableaux sont pour les données tabulaires. N'utilisez pas de balisage de
  tableau uniquement pour aligner visuellement le contenu.

</Callout>

## Questions courantes [#common-questions]

<Accordions type="single">
  <Accordion title="Le composant Table doit-il récupérer des données ?">
    Non. Table est une primitive de rendu. La récupération, le filtrage, le tri et la pagination doivent résider dans le calque de caractéristiques.
  </Accordion>

<Accordion title="Quand devrais-je utiliser le modèle de table de données à la place?">
  Utilisez le modèle de table de données lorsque la table a besoin de filtres,
  de chargement, de vide, d'erreur, de pagination, d'actions de ligne et de
  comportement spécifique au produit.
</Accordion>

<Accordion title="Une ligne peut-elle être cliquable ?">
  Oui, mais rendez l'interaction claire et le clavier accessible. Évitez de
  cacher plusieurs actions derrière un seul clic ambigu.
</Accordion>

  <Accordion title="Combien de colonnes une table doit-elle avoir ?">
    Gardez le nombre raisonnable. Si le tableau devient trop large ou trop difficile à analyser, déplacez les détails secondaires dans un panneau latéral, une boîte de dialogue ou une page de détails.
  </Accordion>
</Accordions>
