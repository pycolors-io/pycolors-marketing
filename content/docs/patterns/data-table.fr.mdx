## Vue d’ensemble [#overview]

Les tableaux de données sont un modèle de tableau de bord SaaS de base.

Ils alimentent les vues d'administration, les écrans de facturation, les listes de clients, les journaux, les abonnements, les projets, les factures et les flux de travail opérationnels. Une table prête pour la production n'est pas seulement des lignes et des colonnes. C’est une interface complète pour comprendre, filtrer, agir et naviguer dans les données structurées.

Utilisez ce modèle lorsque les utilisateurs ont besoin de :

- numériser des enregistrements reproductibles
- Comparer les valeurs structurées
- filtrer ou rechercher un jeu de données
- Agir sur des lignes individuelles
- Se déplacer à travers les résultats paginés
- récupérer des états de chargement, de vide et d'erreur

<Callout title="Pourquoi cela compte">
  Les tableaux sont les endroits où la complexité du produit devient visible. Si
  le chargement, les filtres, les actions en ligne et la pagination sont
  incohérents, l’ensemble du tableau de bord est moins fiable.

</Callout>

## Modèle mental [#mental-model]

> La table rend la structure. La couche de données possède la vérité. La barre d'outils contrôle l'intention. Le pied de page gère la navigation.

| Zone              | Responsabilité                                                |
| ----------------- | ------------------------------------------------------------- |
| En-tête           | Contexte de la page et actions principales                    |
| Barre d'outils    | Recherche, filtres, actions en masse et contrôles d'affichage |
| Tableau           | Lignes, colonnes, sélection et rendu des lignes               |
| Actions en ligne  | Actions contextuelles pour un enregistrement                  |
| Footer            | Pagination, comptage et résumé de sélection                   |
| Couche de données | Récupération, tri, filtrage, permissions et mutations         |

<Callout type="info" title="Règle du système">
  Une table ne doit pas posséder la source de données. Continuez à récupérer,
  filtrer, trier, les autorisations et les mutations dans le calque de
  fonctionnalités.

</Callout>

## Étapes [#steps]

<Steps>

<Step>
### Définir l'anatomie [#define-the-anatomy]

Une table de production est composée de zones distinctes. Chaque domaine doit évoluer indépendamment.

```tsx title="components/projects-table.tsx"
export function ProjectsTable() {
  return (
    <section className="space-y-4">
      <ProjectsTableHeader />
      <ProjectsTableToolbar />
      <ProjectsTableContent />
      <ProjectsTableFooter />
    </section>
  );
}
```

Cela permet de garder la table flexible lorsque les exigences du produit augmentent.

</Step>

<Step>
### Conserver les données en dehors de la table [#keep-data-outside-the-table]

La table devrait recevoir des données, des statuts et des rappels. Il ne doit pas posséder de règles de récupération, de contrôle d'autorisation ou de mutation.

```tsx title="features/projects/projects-table-container.tsx"
export function ProjectsTableContainer() {
  const projects = useProjects();
  const filters = useProjectFilters();

  return (
    <ProjectsTable
      data={projects.data}
      status={projects.status}
      filters={filters.value}
      onFiltersChange={filters.setValue}
      onRetry={projects.refetch}
    />
  );
}
```

La couche de fonctionnalité possède la vérité. La table affiche l'état actuel.

</Step>

<Step>
### Concevoir des états avant les lignes [#design-states-before-rows]

Chaque table a besoin d'états de chargement, de vide et d'erreur explicites.

<Tabs items={["Chargement", "Vide", "Erreur"]}>
  <Tab value="Chargement">
    <DataTableLoading />

</Tab>

<Tab value="Vide">
  <DataTableEmpty />

</Tab>

  <Tab value="Erreur">
    <DataTableError />

</Tab>

</Tabs>

N'ajoutez pas ces états à la fin. Ils définissent la sensation de production de la table.

</Step>

<Step>
### Ajouter des contrôles délibérément [#add-controls-deliberately]

Les filtres et les actions de ligne devraient soutenir la tâche sans que la table se sente encombrée.

Utiliser la divulgation progressive :

- contrôles en ligne pour les filtres fréquents
- `Sheet` pour les filtres avancés
- `DropdownMenu` pour les actions secondaires en ligne
- la confirmation ou la récupération pour des actions destructrices

</Tab>

  <Tab value="Actions en ligne">

</Tab>

</Tabs>

</Step>

</Steps>

## Anatomie [#anatomy]

Une table évolutive a des régions claires.

| Région         | Ce qui y appartient                               | Ce qu'il faut éviter                    |
| -------------- | ------------------------------------------------- | --------------------------------------- |
| En-tête        | titre, description, action primaire               | logique de récupération de données      |
| Barre d'outils | recherche, filtres, actions groupées              | tout contrôle possible à la fois        |
| Tableau        | lignes, colonnes, sélection, actions de lignes    | règles d'affaires et logique de serveur |
| Footer         | pagination, nombre d'éléments, nombre sélectionné | État de navigation caché                |

<Callout title="Pourquoi cela compte">
  Lorsque les responsabilités sont séparées, la table peut se développer sans
  devenir un seul élément fragile.

</Callout>

## États [#states]

Une table de production gère plus que le chargement et le succès.

| État       | Composante                | Objectif                                                |
| ---------- | ------------------------- | ------------------------------------------------------- |
| Chargement | `Skeleton`                | Conserver la forme alors que les données sont attendues |
| Vide       | `EmptyState`              | Expliquer les résultats valides vides                   |
| Erreur     | `Alert`                   | Expliquer l'échec et la récupération                    |
| Filtrage   | État de la barre d'outils | Afficher clairement les contraintes actives             |
| Mutation   | État en ligne ou toast    | Confirmer les progrès et le rétablissement de l'action  |
| Paginating | Footer state              | Gardez la navigation prévisible                         |

N'utilisez jamais le même modèle de rétroaction pour chaque état. Le chargement des données, la suppression d'une ligne, l'enregistrement des filtres et la modification des pages sont des expériences utilisateur différentes.

## Guide de décision [#decision-guide]

Utilisez ce modèle si :

- la page affiche des données structurées reproductibles
- les utilisateurs doivent numériser, filtrer, comparer ou agir sur les lignes
- la table apparaît dans un tableau de bord ou une surface d'administration
- Les états de chargement, de vide et d'erreur sont importants
- pagination, actions en ligne ou actions en masse sont requises

Évitez ce modèle si:

- Le contenu est éditorial ou marketing
- Les données sont mieux représentées sous forme de cartes, de chronologie ou de flux.
- l'utilisateur n'a besoin que d'une seule valeur de résumé
- Le scan mobile-first est plus important que la comparaison tabulaire
- la table cacherait l'action du produit principal

## Liste de contrôle de production [#production-checklist]

Avant d'expédier une table de données, confirmez que :

- loading préserve la mise en page attendue
- L'état vide explique le résultat et l'action suivante
- état d'erreur inclut la récupération ou réessayer
- La pagination est contrôlée et prévisible
- Les filtres peuvent être nettoyés
- Les filtres actifs sont visibles
- les actions de ligne sont accessibles au clavier
- Les actions destructrices nécessitent une confirmation ou une récupération
- L'état de sélection est clair lorsque des actions en masse existent
- Le comportement mobile est défini

## Questions courantes [#common-questions]

<Accordions type="single">
  <Accordion title="La table doit-elle récupérer ses propres données ?">
    Préférez garder les données en dehors de la table. La table doit rendre les données et exposer les callbacks. La couche de fonctionnalité doit posséder la récupération, les autorisations, le filtrage et les mutations.
  </Accordion>

<Accordion title="Quand les filtres doivent-ils se déplacer dans un panneau latéral?">
  Déplacez les filtres dans un panneau latéral lorsque la barre d’outils est
  encombrée, que les filtres sont secondaires ou que l’expérience mobile
  nécessite un modèle d’interaction plus propre.
</Accordion>

  <Accordion title="Les actions de ligne doivent-elles toujours être dans une liste déroulante ?">
    Utilisez une liste déroulante pour les actions secondaires ou contextuelles. Gardez l'action de ligne principale visible uniquement lorsque c'est la principale raison pour laquelle les utilisateurs visitent la table.
  </Accordion>
</Accordions>
