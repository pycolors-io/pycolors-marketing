## Comment les navires PyColors [#how-pycolors-ships]

PyColors est conçu pour se déplacer rapidement **Sans devenir instable**.

Le modèle de publication sépare deux choses qui se mélangent souvent :

- **packages** Versioning technique
- **écosystème** à la progression du produit

Cette séparation permet à PyColors de publier des mises à jour de paquets précises tout en communiquant la progression du produit de manière à ce que les clients et les développeurs puissent comprendre.

<Callout title="Idée de base">
  Les paquets suivent la vérité technique. L’écosystème communique l’élan
  produit.

</Callout>

### Versioning des paquets [#package-versioning]

Paquets publics tels que `@pycolors/ui`, `@pycolors/tokens`, et les paquets de configuration partagés suivent **Versioning sémantique**.

```txt title="semver.txt"
MAJOR → breaking changes
MINOR → new features, backward compatible
PATCH → fixes and small improvements
```

Exemples :

```txt title="examples.txt"
1.0.3 → bug fixes
1.1.0 → new components or backward-compatible features
2.0.0 → breaking changes
```

### Source de vérité [#source-of-truth]

Les informations de publication sont divisées par audience et par objectif.

| Surface        | Objet                                                        |
| -------------- | ------------------------------------------------------------ |
| GitHub         | Détails de la version technique                              |
| `CHANGELOG.md` | Modifications au niveau des packages générées par Changesets |
| `/changelog`   | Mises à jour hebdomadaires de l'écosystème                   |
| `/roadmap`     | Direction des produits et travaux à venir                    |

<Callout type="info" title="Pourquoi ce split">
  Les développeurs ont besoin de changements techniques précis. Les clients ont
  besoin d'une progression claire du produit. PyColors garde les deux visibles
  sans les mélanger.

</Callout>

## Ecosystem Releases [#ecosystem-releases]

Le site Web communique une cadence de diffusion hebdomadaire.

Cela inclut les mises à jour dans :

- PyColors UI
- Tokens PyColors
- Starter Free
- Starter Pro
- modèles
- documentation
- patrons
- pages marketing
- plate-forme et couches de livraison

Les colis sont expédiés quand ils sont prêts.

L'écosystème est livré comme un récit de produit clair.

> La vérité technique reste précise. Le progrès du produit reste compréhensible.

## Flux de travail Changesets [#changesets-workflow]

Toutes les versions des paquets suivent le même modèle opérationnel.

<Steps>
  <Step>
    ### Apporter des changements dans le monorepo [#make-changes-in-the-monorepo]

    Le développement se produit dans le noyau PyColors monorepo où les packages, les applications, les modèles, les documents et la configuration partagée évoluent ensemble.

</Step>

  <Step>
    ### Ajouter un changeset [#add-a-changeset]

    Chaque modification au niveau du paquet obtient un jeu de modifications avec le type de version correct : patch, mineur ou majeur.

</Step>

  <Step>
    ### Fusionner à main [#merge-to-main]

    Les modifications sont examinées et fusionnées via le flux de travail normal du référentiel.

</Step>

  <Step>
    ### Version et changelog sont mis à jour [#version-and-changelog-are-updated]

    CI met à jour les versions des paquets et génère des entrées de journal des modifications au niveau des paquets.

</Step>

  <Step>
    ### Publier et publier [#publish-and-release]

    CI publie des paquets et crée des versions GitHub le cas échéant.

</Step>

</Steps>

## Pourquoi cette approche [#why-this-approach]

La plupart des projets tombent dans l'un des deux problèmes de publication:

- les rejets sont trop lents, donc le produit se sent inactif
- Les versions sont trop chaotiques, donc les utilisateurs perdent confiance

PyColors équilibre les deux:

- itération technique rapide au niveau du paquet
- Une communication prévisible au niveau de l’écosystème

Cela crée un rythme de publication qui soutient à la fois la confiance des développeurs et la confiance commerciale.

### Ce que cela garantit [#what-this-guarantees]

Cette politique est conçue pour fournir :

- Mises à jour prévisibles
- versioning clair
- Pas de changements de rupture cachés
- Progrès visibles du produit
- Historique des paquets traçables
- séparation entre la vérité technique et la narration du produit

<Callout title="Principe de confiance">
  Un produit de développeur premium ne devrait pas seulement être livré
  fréquemment. Cela devrait rendre les progrès faciles à comprendre.

</Callout>
