If installed PyColors components render as plain content, check whether their
utilities exist in the generated CSS. In the Tailwind v4 reproduction below,
adding `@source` for the installed package fixes the missing styles. Installing
the package and passing a production build are not enough.

For `app/globals.css`, the complete stylesheet is:

```css title="app/globals.css"
@import "tailwindcss";
@import "@pycolors/tokens/tokens.css";
@source "../node_modules/@pycolors/ui/dist";

@custom-variant dark (&:where(.dark, .dark *));

@layer base {
  * {
    @apply border-border;
  }
  body {
    @apply bg-background text-foreground;
  }
}
```

Already importing Tailwind and PyColors tokens? Add only the missing `@source`
line. Keep the imports at the top; do not duplicate the token mappings.

[Read the PyColors UI installation guide](/docs/ui/installation) for the
canonical setup and requirements.

production consumer described below. Original publication: March 17, 2026._

## Use the path relative to your stylesheet

The two tested layouts need different registrations:

| Global stylesheet     | Source registration                               |
| --------------------- | ------------------------------------------------- |
| `app/globals.css`     | `@source "../node_modules/@pycolors/ui/dist";`    |
| `src/app/globals.css` | `@source "../../node_modules/@pycolors/ui/dist";` |

Tailwind v4 ignores `node_modules` during automatic detection. An explicit
`@source` opts this package in; its path starts at the stylesheet, not the
terminal's working directory. See [Tailwind's source detection documentation](https://tailwindcss.com/docs/detecting-classes-in-source-files).

Use the installed package's `dist` directory for this npm consumer. A workspace
that imports local source has a different location: resolve that location from
its stylesheet. Scanning an entire monorepo or all of `node_modules` is unnecessary.

## What the failing build actually showed

The example uses the public `Card` and `Button` exports without adding their
internal classes to the app. Both the failing and corrected versions passed
TypeScript checking and a production build.

| Condition                                      | Generated CSS                                       | Browser result                                                                                         |
| ---------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Tokens loaded, no library registration         | No `.inline-flex`, `.bg-primary` or `.bg-card` rule | Link styled as a Button remains inline, transparent and unpadded                                       |
| Wrong relative source path                     | Same missing rules                                  | Same unstyled components                                                                               |
| Correct source path                            | All three rules present                             | Button uses `inline-flex`, a 36px height and 8px/16px padding; Button and Card have themed backgrounds |
| Correct source, primary/card mappings disabled | Layout rule present; both background rules absent   | Button keeps its layout but both surfaces are transparent                                              |

The source-path results were verified for **both stylesheet locations**. The
last row is a separate negative control: the test resets only
`--color-primary` and `--color-card` to `initial` inside `@theme`. It leaves the
underlying CSS variables loaded. Do not add that reset to your application.

These utilities were never generated in the missing-source case; they were
not existing component styles that Tailwind subsequently removed. If the rule
is present but crossed out in browser DevTools, inspect the cascade and
competing CSS instead of adding more scan paths.

## Check production CSS, then the browser

Temporarily remove the `@source` line from the disposable example, build again,
and inspect `.next/static/css`. Restore the correct line and rebuild. Search
for `.inline-flex`, `.bg-primary` and `.bg-card` in the emitted CSS, not just in
the component's DOM class attribute. All three should appear after the correction.

Serve the production output with `pnpm start`. In DevTools, inspect the computed
styles of `[data-slot="button"]` and `[data-slot="card"]`. For the corrected
example, Chromium measured these background colors:

| Surface | Light                  | With `.dark` on the document root |
| ------- | ---------------------- | --------------------------------- |
| Button  | `oklch(0.49 0.23 292)` | `oklch(0.68 0.19 292)`            |
| Card    | `oklch(0.99 0 0)`      | `oklch(0.19 0.008 285)`           |

Wait for color transitions to finish before measuring. Your application owns
its existing theme selection; PyColors does not require a new provider.
This check covers this composition's styles, not an accessibility certification.

From a PyColors repository checkout with its dependencies installed, the
explicit network integration check repeats all eight combinations:

```bash
pnpm --filter @pycolors/ui exec playwright install chromium
pnpm test:ui-consumer
```

It installs the locked public dependencies in a temporary external project,
checks generated selectors and Chromium styles, and requires the negative
controls to fail the same styling assertion that the corrected cases pass.
It uses the existing Playwright dependency and is separate from ordinary unit
tests. The fixture README records its scope and observed results.

## Distinguish source detection from token setup

The public `@pycolors/tokens/tokens.css` import already supplies the theme values
and their Tailwind v4 semantic mappings. A `--primary` value alone does not
define a `bg-primary` utility. The mapping and a detected class are both needed.
Our separate negative control demonstrates this: layout survives, while the
two intentionally unmapped background utilities disappear.

Keep the supported import once, and remove conflicting theme resets rather
than copying a second mapping layer. Continue with the
[theming guide](/docs/ui/theming) or
[semantic design tokens article](/blog/semantic-design-tokens-tailwind-v4)
when the remaining problem is theme values rather than missing utilities.

In your own components, write complete class names. Tailwind scans text; it
does not evaluate strings such as `bg-${color}-500`. Map a prop to complete
static alternatives instead. This follows the
[official class detection guidance](https://tailwindcss.com/docs/detecting-classes-in-source-files#dynamic-class-names).

## A note for readers of the earlier Tailwind v3 recipe

The earlier version of this article used `tailwind.config` content paths, a
Tailwind v3 convention. Tailwind v4 does not automatically detect JavaScript
configuration files; see the [upgrade guide](https://tailwindcss.com/docs/upgrade-guide#using-a-javascript-config-file).
The tested PyColors setup here uses v4 CSS configuration. This reproduction
does not establish compatibility of these package versions with Tailwind v3.

Package download failures, ESLint configuration and deployment logs are separate
diagnostics. Changing from pnpm to npm does not supply a missing source path;
this entire reproduction uses pnpm.

## Final checks

- Resolve the narrow package source path from the actual stylesheet location.
- Import the public tokens stylesheet once and preserve its semantic mappings.
- Verify generated utilities in a fresh production build.
- Inspect computed component styles in both themes; investigate overrides when rules exist.
- Keep complete class names and avoid diagnostic files contaminating source detection.
