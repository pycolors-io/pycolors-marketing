## The problem

At first, I wanted my SaaS starter to feel complete.

Not just useful.
Not just production-shaped.
**Complete.**

That instinct sounds good, but in practice it pushed me toward the wrong kind of complexity:

- more abstraction than immediate value
- more optionality than real product leverage
- more architecture than shipping speed

At some point, I realized I was no longer building a strong foundation for real SaaS products.
I was building a framework for hypothetical future needs.

That was the turning point.

## Why this matters

A SaaS starter is not valuable because it can theoretically adapt to everything.

It is valuable because it removes the expensive setup work that slows real product teams down:

- authentication surfaces
- dashboard structure
- settings architecture
- billing entry points
- coherent product layout
- reusable UI primitives

The more I focused on those concrete foundations, the more useful the starter became.

## What I was overengineering

Here are the patterns I started removing.

### 1. Too many abstraction layers

I was tempted to generalize too early.

Examples:

- wrappers around simple product sections
- generic feature modules before having repeated use cases
- indirection between pages, state, and UI where plain composition was enough

This made the starter look “architected”, but not necessarily easier to use.

The problem with early abstraction is simple:

> if the variation is not real yet, the abstraction is usually fake.

### 2. Optional systems with no current buyer value

I also started adding systems that felt impressive but did not solve the immediate problem of shipping faster:

- advanced permission scaffolding too early
- placeholder enterprise patterns without product demand
- configurable surfaces that were never actually configured

These things create surface area, but not always leverage.

A good starter should reduce the distance between “clone repo” and “start building your product”.

### 3. Generic dashboards

Generic dashboards are one of the fastest ways to make a starter feel fake.

A serious starter does not need a random KPI grid, a fake activity feed, and placeholder charts.

It needs:

- clear information hierarchy
- realistic empty states
- good defaults for common product surfaces
- room for real product logic

That is a very different goal.

## What I kept

I did not remove complexity blindly.

I kept the parts that create real product leverage.

### 1. Authentication surfaces

A SaaS starter should help developers skip repetitive auth work.

That means keeping strong foundations for:

- sign in
- sign up
- password reset
- protected app areas
- session-aware layouts

### 2. Settings architecture

Settings are often underestimated, but they are one of the most stable and valuable product surfaces in SaaS.

A good starter should already have structure for:

- profile
- account
- security
- billing
- organization-ready evolution later

### 3. Billing entry points

Even if the billing engine is not fully wired yet, the UX surface matters early.

Developers need a serious foundation for:

- plan presentation
- upgrade entry points
- billing settings
- invoice and trust patterns later

### 4. A coherent layout system

Instead of adding more abstraction, I put more effort into consistency:

- public marketing pages
- authenticated app shell
- settings navigation
- dashboard hierarchy
- reusable sections and cards

That creates much more value than speculative flexibility.

## The rule I use now

This is the rule I use for PyColors now:

> if a feature does not make shipping faster, clarity better, or product structure stronger, it probably does not belong in the starter yet.

That rule removes a lot of noise.

## What this changed in practice

Once I simplified the starter, the direction became much clearer.

Instead of asking:

“How can this support every possible SaaS?”

I started asking:

“How can this help a developer ship a credible SaaS product faster this week?”

That shift changed everything.

It improved:

- maintainability
- product clarity
- onboarding speed
- implementation confidence
- upgrade path between free and pro


## A source-level check: is the billing screen actually connected?

A starter can display an "Active" subscription, invoice rows, and an attractive billing layout without processing a payment. **A rendered billing state is evidence of the interface, not evidence of a billing integration.** Before selecting a starter, identify which system owns each value and what test would prove it is real.

For a concrete example, consider the [public Starter Free billing source](https://github.com/pycolors-io/pycolors-starter-free/blob/a65f170b4216faf6647a41a4717a0ca8d64a1376/app/%28app%29/billing/page.tsx). The file inspected on November 2, 2026, contains four independently checkable signs of a preview:

- `MOCK_INVOICES` provides fixed example invoice records.
- A local `plan` object includes a literal `active` status. That badge is not derived from a provider or entitlement lookup.
- The page explicitly tells readers that amounts and invoices are fictional and that no payment service is connected.
- **Manage billing** is a disabled button, rather than a link to a working customer portal.

These are deliberate, honest boundaries in Starter Free. They make its billing layout useful for evaluating copy, navigation, loading states, and the information hierarchy. They do **not** establish provider configuration, account ownership, payment settlement, customer access, or subscription lifecycle handling.

### Reproduce the source audit without a payment account

From a checkout of the [public Starter Free repository](https://github.com/pycolors-io/pycolors-starter-free), run this original, dependency-free Node.js check. It inspects one source snapshot; it does not connect to Stripe, create test payments, or inspect private code.

```js title="check-billing-preview.mjs"
import assert from "node:assert/strict";
import { readFileSync } from "node:fs";

const source = readFileSync("app/(app)/billing/page.tsx", "utf8");

const evidence = {
  fixtureInvoices: /\bconst MOCK_INVOICES\b/.test(source),
  literalPlan: /\bconst plan = \{[\s\S]*?\bstatus: "active"/.test(source),
  demoDisclosure:
    /Sample billing workspace/.test(source) &&
    /No\s+payment service is connected\./.test(source),
  disabledAction:
    /<Button size="sm" type="button" disabled>\s*Manage billing/.test(
      source,
    ),
};

for (const [name, observed] of Object.entries(evidence)) {
  assert.ok(observed, "Expected demo evidence missing: " + name);
  console.log("PASS: " + name);
}
```

```sh
node check-billing-preview.mjs
```

All four checks matched the current public mirror source during this article's source review. The test file itself has **not** been run in a complete Starter Free checkout or in the repository's declared Node 24/pnpm environment for this draft. These assertions intentionally depend on present source wording; a harmless refactor may require updating them.

A positive result answers a narrow question: *does this source still disclose and implement the known demo boundary?* It does **not** prove the absence of every backend integration elsewhere, or establish whether another starter has secure server-side billing. Likewise, if a check fails after a change, inspect the source before treating that failure as a regression.

### Ask for different evidence when the feature must be real

| Reader question | Evidence to look for |
| --- | --- |
| Can I evaluate the billing screen? | Sample plans, responsive layout, accessible controls, clear demo disclosure |
| Can a customer actually sign in? | A configured identity provider, server-validated sessions, and protected-route tests |
| Can a subscription change access? | Provider test-mode events, server-side entitlement checks, replay/failure handling, and an observed test workflow |
| Can users find their own invoices? | An authorized customer-to-invoice lookup and tests that prohibit cross-account access |
| Can I launch the product? | Environment-specific integration, migrations, security review, operational checks, and an approved launch process |

No screenshot, passing UI test, or disabled portal button substitutes for those backend checks. Conversely, a deliberately mocked surface is not a defect when the goal is to evaluate the interface before choosing a backend.

**Verification checklist:** inspect the current public files rather than relying on screenshots; distinguish literal sample values from server responses; try the demo with fabricated data only; check whether actions are disabled or simulated; require separate test-mode and authorization evidence for any connected claim; record the installed versions when running a real integration test.

For the canonical setup and product-boundary details, use [Starter Free getting started](/docs/starter/getting-started) and [the SaaS starter evaluation guide](/guides/production-ready-saas-starter). The code excerpt above is not copied from the Pro starter, does not authenticate a user, and does not handle real billing.

**Checked source context (November 2, 2026):** the public Starter Free manifest declares version `1.2.3`, Next.js `16.4.2`, React `^19.3.1`, Node `>=20.19.0`, and pnpm `10.32.1`. These are **manifest declarations, not tested install versions**. The official [Node.js assertion](https://nodejs.org/api/assert.html) and [file-system](https://nodejs.org/api/fs.html) references describe the built-in APIs used above.

## Final takeaway

I did not stop overengineering because simplicity looks better.

I stopped because **a starter becomes more useful when it is closer to real shipping needs and farther from imaginary future abstraction**.

That is the direction behind PyColors:

- stronger product surfaces
- less fake complexity
- faster path to a real SaaS
